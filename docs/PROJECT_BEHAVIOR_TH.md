# หลักการทำงาน Pick Productivity V3 และ Sort Monitoring ใน Google Sheets

เอกสารนี้เป็นจุดอ้างอิงร่วมกันก่อนแก้หน้าเว็บ สูตร หรือตัวกรอง อัปเดตเมื่อ 15 ตุลาคม 2569 หลังตรวจโค้ดใน repository, `data/targets.json` และ Google Sheets สดที่ผู้ใช้ให้มา

> แหล่งข้อมูลหลักคือ [New_Z856 Performance Picking by Staff and Shift_V2](https://docs.google.com/spreadsheets/d/1PMnlyYHswnV0nE73Alxh-ocIFtTipB9LMzACdNM9GFs/edit) (locale ไทย, เวลา Asia/Bangkok) ตรวจ Apps Script จากเมนู Extensions ของชีตแล้ว: source ใช้ `CACHE_VERSION` v52; Web App deployment เดิมอัปเดตเป็น Script version 61 เมื่อ 15 ต.ค. 2569 โดยคง deployment ID/URL เดิม รันในฐานะเจ้าของและเปิดสิทธิ์ “ทุกคน”

## ภาพรวม

เว็บนี้เป็นเครื่องมือปฏิบัติการสำหรับดูปริมาณงานหยิบและ Productivity ของทีมคลังสินค้า ส่วนใน Google Sheets ยังมีระบบ Sort Monitoring แยกอีกชุดหนึ่ง ทั้งสองชุดใช้ข้อมูล Sort ร่วมกันบางส่วน แต่หน่วยวัดและเป้าหมายไม่เหมือนกัน:

- **Pick Productivity V3:** ใช้ค่า `AVERAGE` ใน `Results Master!AF` หน่วย Pick/ชั่วโมง และ Target ตามประเภท/โซน
- **Sort Monitoring:** แปลงจำนวน WMS เป็น UOM จาก `UOM_Master` แล้วสรุป UOM/ชั่วโมง เป้าทีมในแท็บ `Dashboard` คือ 200 UOM/ชั่วโมง

จึงไม่ควรเทียบค่า Target 200 UOM/ชั่วโมงใน Dashboard ของชีตกับ Target Pick/ชั่วโมงของหน้าเว็บโดยตรง

คำถามหลักของหน้าเว็บแยกกันดังนี้:

- **Total Pick** บอกปริมาณหยิบรวมจากข้อมูลต้นทาง
- **Productivity** บอกค่าเฉลี่ยหยิบต่อชั่วโมงที่ชีตคำนวณและบันทึกไว้
- **Target / Efficiency** ใช้เทียบผลกับเป้าของภาพรวม ประเภทงาน หรือโซน
- **Not Found / ตรวจข้อมูล** ชี้จุดที่ควรตามแก้ โดยผลงานเดิมยังอยู่ในแหล่งข้อมูล

หน้าตาและระบบเมนูอิง V2 ส่วนการรวมข้อมูลหลักอิง V1 และมีหน้าวิเคราะห์ที่คำนวณจากแถวดิบเพิ่มเข้ามา ตัวเลขจึงอาจใช้เส้นทางคำนวณต่างกันตามหน้า โดยเฉพาะโซนที่ไม่อยู่ในผังปัจจุบันและ Pick to Sort โซน BE

## เส้นทางข้อมูล

1. `js/source.js` ดาวน์โหลดแท็บที่กำหนดเป็น CSV และแปลงวันที่/แถวข้อมูล
2. `js/data-client.js` เริ่มจาก IndexedDB หรือ `data/snapshot.json` แล้วพยายามโหลด Google Sheets ล่าสุด
3. `js/data-worker.js` ให้ Web Worker กรอง Results Master ตามระบบ/กะ/Owner แล้วเรียก `V1Engine.buildIndex()`; วันที่ใช้กรองตอนสร้างผล Dashboard
4. `js/script.js`, `js/insights.js` และไฟล์ `js/v2-*.js` ใช้ข้อมูลชุดเดียวกันสร้างหน้าจอ ตาราง และกราฟ
5. ถ้าโหลดสดไม่สำเร็จ เว็บคงข้อมูลสำรองเดิมและแจ้งเตือน ไม่เปลี่ยนผลเป็นศูนย์
6. การอ่านหลักของหน้าเว็บไม่ได้เรียก Apps Script `doGet()`; หน้าเว็บอ่าน CSV จาก Google Sheets โดยตรง ส่วน Apps Script ใช้รับการเขียน Target/Weight/ทะเบียน/BE History ตามที่ตั้งค่าไว้

ต้องเปิดผ่าน HTTP เช่น `node tools/serve.cjs` หรือ `START.cmd` เพราะเว็บใช้ Web Worker

`Results Master` มีคอลัมน์สำคัญดังนี้: B ชื่อสำรอง, C วันที่, D User ID, E Total pick, F Avr/Hour, G Operating time, H–AE ยอด 24 ช่วงเวลา, AF AVERAGE, AG Shift, AH Position, AI สังกัด, AJ BU, AK Pick Type, AL Count, AM Check, AN Duplicate, AO week, AP month, AQ รายวัน/รายเดือน

สูตร `Results Master!AF` ที่อ่านจากชีตสดคือ:

```text
=IF(D2="","",IF(AK2="ช่วยงานส่วนอื่น","Not Count",IF(AND(G2>3,F2<1000),F2,"Not Count")))
```

ความหมายคือไม่มี User ID ให้ค่าว่าง; งาน `ช่วยงานส่วนอื่น` ให้ `Not Count`; นอกนั้นใช้ F เป็น Productivity เมื่อชั่วโมง G **มากกว่า 3** และ F **น้อยกว่า 1,000** เท่านั้น เงื่อนไขเป็นแบบเข้มงวด: G=3 หรือ F=1,000 จะไม่ผ่าน เว็บไซต์ใช้ AF ตามที่ชีตให้มา ไม่คำนวณใหม่จาก E ÷ G และไม่ปรับชั่วโมง

ข้อควรระวัง: AF ไม่ได้เป็นสูตรทุกแถว จากช่วง AF2:AF29698 ที่ตรวจ มี 16,254 เซลล์เป็นสูตร (8,944 ให้ค่าผลลัพธ์ และ 7,310 ว่างตามเงื่อนไข) กับ 12,443 เซลล์ที่เป็นค่าคงที่ สูตรข้างต้นจึงยืนยันกติกาของแถวที่มีสูตร แต่ไม่ได้พิสูจน์ว่าค่าคงที่ย้อนหลังทุกแถวคำนวณด้วยกติกาเดียวกัน อย่าเติม/เขียนทับทั้งคอลัมน์ AF โดยไม่ตกลงการจัดการค่าประวัติก่อน

`2ND` มีสูตรดึงวันเริ่มงานจาก `Data_Employees` และดึง Type Pick/Owner จาก `Zone_V2!A:C`; `Results Master!AG:AK` จึงเป็น metadata ที่ผูกด้วย User ID จาก `2ND` อีกชั้นหนึ่ง สถานะ `2ND!I` ใช้วันที่เริ่มงาน + 60 วันเพื่อเปลี่ยน Training เป็น Ready ส่วนหน้าเทรนของเว็บอ่านทะเบียน `Update name` และมีกฎเลือกช่วงของตัวเองตามหัวข้ออายุงาน/Training ด้านล่าง

## ตัวกรองที่ใช้ร่วมกัน

- **วันที่:** ใช้วันที่ในคอลัมน์ C ช่วงที่เลือกเป็นวันที่เริ่มและสิ้นสุดแบบรวมวัน ระบบเริ่มที่วันก่อนหน้าและข้ามวันอาทิตย์ แล้วเลือกวันทำงานล่าสุดที่มีข้อมูลเมื่อวันเป้าหมายไม่มีแถว
- **ระบบ:** อ่านจาก AK; Pick to Sort อยู่ใน BPS ตั้งแต่ 8 มิ.ย. 2569 เป็นต้นไป หน้าภาพรวมแบบ All ยังรวมแถว AF ของทุกประเภทตามปกติ
- **กะ:** อ่านจาก AG ตาม Sheet ไม่อนุมานจากเวลา ค่าว่าง, `Not Found`, `Not Found Data`, `#N/A` และ `-` ถูกรวมเป็น `Not Found` ในตัวกรอง
- **Owner:** โค้ดอ่านจาก AJ ซึ่งหัวคอลัมน์คือ BU; `Max Mart` และชื่อที่มี `Max Mart` แสดงเป็น Mart, `Punthai` และ `GFA` เป็นกลุ่มของตนเอง ค่าที่เหลือเป็น Owner ไม่ระบุ
- **วิธีคำนวณ:** `ปกติ` หรือ `Weight%` ตามชุดน้ำหนักที่ตั้ง

การเปลี่ยนระบบ/กะ/Owner/วิธีคำนวณจะรวมข้อมูลใหม่ใน Worker โดยไม่ต้องโหลด CSV ใหม่ ตัวกรองวันที่ก็ใช้กับหน้าส่วนใหญ่ แต่หน้าเทรนกางงวดทั้งหมด, หน้าเดือนแสดงทุกงวด และการ์ดตรวจซ้ำสแกนทั้งประวัติ

## กติกาคำนวณ

### Total Pick

สูตรหลักคือผลรวม E ของแถวที่มีวันที่และผ่านตัวกรอง แม้ AF จะเป็น `Not Count` หรือ Position จะมีปัญหา แถวดังกล่าวยังมี Total Pick ให้ตรวจสอบได้

ข้อยกเว้นคือ BE: ใช้ Sort_Data เป็นแหล่งคำนวณกะและยอดทีม ไม่ใช้ Results Master ทำยอด BE; เมื่อไม่มีข้อมูลดิบจึงใช้ได้เฉพาะสรุปที่บันทึกไว้ใน V3 History ตามกะที่มี split จริง

### Productivity โหมดปกติ

รูปแบบพื้นฐานคือ:

```text
Productivity = ผลรวม AF ของแถวที่เข้าเงื่อนไข ÷ จำนวนแถวที่เข้าเงื่อนไข
```

ไม่มีการเฉลี่ยค่าเฉลี่ยรายวันซ้ำ เมื่อรวมหลายวันให้รวมผลรวม AF และจำนวนแถวก่อน แล้วหารครั้งเดียว

**เงื่อนไข AF และ Position ต่างกันตามเส้นทางโค้ด:**

| เส้นทาง | เงื่อนไขที่นับ Productivity |
|---|---|
| `v1-engine.js` ดัชนีหลัก/ภาพรวม | AF > 0 และ Position จับคู่กับ `ZONE_GROUPS` ภายใน V1 engine |
| `metrics.js` ที่หน้าวิเคราะห์แถวดิบใช้ | AF > 0 และ AH มีรหัสใน `VALID_ZONE_CODES` |
| `insights.js` หน้าไม่ถึงเป้า | AF > 0; ถ้า Position จับคู่โซนไม่ได้ จะจัดเป็น Not Found และเทียบ Overall Target |
| Weight% | ต้องจับคู่กับโซนที่มีน้ำหนักมากกว่า 0 ในชุดผัง/น้ำหนักปัจจุบัน |

ดังนั้นแถว `Not Count` ไม่เข้าค่าเฉลี่ย แต่บางแถวที่ AF > 0 และ Zone ผิดรูปแบบอาจถูกนับในหน้าไม่ถึงเป้า ต่างจากภาพรวมและหน้าที่ใช้ `metrics.aggregate()` หน้าไม่ถึงเป้ายังคำนวณจากค่า AF ปกติแม้เลือก Weight% เพราะหน้านี้รวม AF เองและไม่เรียก `aggregateForMode()`

### การปัดและการตัดสินผ่าน

- ตัวเลข Productivity ที่เห็นในหลายการ์ด/ตารางปัดเป็นจำนวนเต็ม; Efficiency แสดงทศนิยม 1 ตำแหน่ง
- ค่าใน V1 index ถูกปัดเป็นทศนิยม 1 ตำแหน่งก่อนส่งให้ `renderDashboard()` แล้ว `applyCurrentTargets()` ใช้ค่านั้นตั้งสถานะใหม่ จึงอาจมีขอบ Target ที่การ์ดภาพรวมตัดสินจากค่า 1 ตำแหน่ง
- หน้าวิเคราะห์ที่รวมแถวดิบ เช่น Efficiency/รายบุคคล เปรียบเทียบค่าเฉลี่ยดิบกับ Target
- เกณฑ์ทั่วไปคือ `Productivity >= Target` ผ่าน และเท่ากับเป้านับว่าผ่าน แต่ความละเอียดที่ใช้ตัดสินยังไม่เหมือนกันทุกเส้นทางตามข้อข้างบน

### Weight%

โหมดนี้เป็นสูตรทางเลือก ไม่เปลี่ยน Total Pick, จำนวนแถว, จำนวนคน หรือชั่วโมง:

1. คำนวณค่าเฉลี่ย AF แยกตาม Zone
2. เฉลี่ย Zone ตาม Weight% ของ Type โดยใช้เฉพาะ Zone ที่มีข้อมูลและมีน้ำหนักมากกว่า 0 แล้วหารด้วยน้ำหนักที่ใช้จริง
3. เฉลี่ย Type ตาม Weight% ภาพรวม โดยใช้เฉพาะ Type ที่มีข้อมูล แล้วหารด้วยน้ำหนัก Type ที่ใช้จริง

ค่าเริ่มต้นใน `data/targets.json`:

| ชั้น | น้ำหนัก |
|---|---|
| Overall | Full Rack 37% · Half Rack 48% · Micro Rack 15% |
| Full Rack | AG 0% · AH-AI 30% · AL-BL-BM-AM 20% · BE 50% |
| Half Rack | AF 30% · AJ-AK 10% · AN-CA-BN-DA 10% · BG-BH 5% · BI-BK 5% · CB-DB-DC-CC 10% · DD-DE 10% · CD-CE 10% · CF-DF 10% |
| Micro Rack | EA 60% · FA 40% |

BE ถูกรวมไว้ในชุด Full Rack สำหรับ Weight% แม้แสดงเป็น Pick to Sort แยกในหน้าปกติ การตั้งค่าน้ำหนักแต่ละชั้นต้องรวมเป็น 100%; น้ำหนัก 0% ไม่ร่วมคำนวณ ค่า Coverage ใช้บอกสัดส่วน Weight% ที่มีข้อมูลจริง

### Target และ Efficiency

```text
Efficiency (%) = Productivity ÷ Target × 100
Gap = Productivity − Target
```

Target กลุ่ม **Overall / Shift / BU, Full Rack, Half Rack, Micro Rack และ Pick to Sort** ใช้ค่าเฉลี่ย Productivity ของเดือนปฏิทินก่อนหน้าเป็น Target; Target Zone ใช้ค่าเฉลี่ยแยกตาม Zone เช่นกัน ส่วน Training ยังคงใช้ Target คงที่จากค่าทีม/ค่า fallback และ Mezzanine ไม่มี Target ในหน้าตั้งค่าแล้ว กลุ่ม Unknown ใช้ Overall Target ในหน้าที่รองรับ Unknown คนหนึ่งคนในหน้าไม่ถึงเป้าถูกจัดเข้ากลุ่มตามโซนหลักที่มีแถวเข้าเฉลี่ยมากที่สุด

หลักคำนวณ Target รายเดือน:

- ใช้ข้อมูลเดือนก่อนหน้าทั้งเดือน เช่น ตุลาคมใช้ 1–30 กันยายน; เป้าแต่ละกลุ่มคำนวณจากค่าเฉลี่ยเลขคณิตของจุด Productivity ที่เข้าเกณฑ์ และคงทศนิยมไว้ในค่าคำนวณ
- Target ที่คำนวณได้ยังเก็บทศนิยมจริงไว้เทียบกับ Productivity; ตอนแสดงผลใช้รูปแบบเดิมคือจำนวนเต็มและปัด .5 ขึ้น โดย `Productivity >= Target` ถือว่าผ่านและเท่ากับเป้านับว่าผ่าน
- Overall / Shift / BU ใช้ค่าเฉลี่ยรวมของจุด Productivity ที่เข้าเกณฑ์ทุกประเภทงาน; Full Rack, Half Rack และ Micro Rack แยกตามประเภท; Pick to Sort แยกจากกลุ่มอื่น; Target Zone แยกตาม Zone
- คิดจากทุก Owner และทุกกะโดยไม่ขึ้นกับ Filter วันที่, Shift, Owner, ระบบ หรือโหมด Weight% ที่ผู้ใช้เลือกอยู่
- Pick to Sort / Zone BE ไม่อ่าน `Results Master`: ใช้ Productivity รายคน/วัน/กะจาก `Sort_Data` เมื่อมีข้อมูลและเข้าเกณฑ์เดิม (ชั่วโมงมากกว่า 3, Productivity มากกว่า 0 และน้อยกว่า 1,000); ถ้าไม่มี `Sort_Data` ของวันนั้นจึงใช้ค่าเฉลี่ยกะจาก `V3 History` หากมี split หรือใช้ค่า Productivity สรุปรายวันเมื่อไม่มี split
- ถ้ากลุ่มหรือ Zone ไม่มีข้อมูลที่ใช้ได้ในเดือนก่อนหน้า จะใช้ค่า fallback ที่โหลดจาก `V3 Target`, `data/targets.json` หรือ IndexedDB ตามลำดับเดิม; ค่าเฉลี่ยรายเดือนคำนวณใหม่เมื่อชุดข้อมูลโหลด/รีเฟรช และไม่เขียนทับค่า Target ที่บันทึกในชีต

ค่า Target ใน `data/targets.json` เป็น **ค่าตั้งต้นสำรองใน repository** ไม่ยืนยันว่าเป็นค่าปัจจุบันจากชีตทีม; Target กลุ่มและ Target Zone ด้านล่างเป็น fallback เท่านั้นเมื่อเดือนก่อนหน้าไม่มีข้อมูล:

## หลักคำนวณ Sort Monitoring ใน Google Sheets

ส่วนนี้เป็นแดชบอร์ดอีกชุดใน Workbook ไม่ใช่หน้า Pick Productivity V3 และไม่ใช้ Target เดียวกัน

### การแปลงรายการ WMS เป็น UOM

`Sort_Data` แถว 3 ลงไปมีรายการจาก WMS และคอลัมน์คำนวณต่อท้าย CS:DC:

| คอลัมน์ | ความหมาย / เงื่อนไข |
|---|---|
| CS `Sort DateTime` | แปลงเวลาจาก BQ; รองรับ serial ของ Sheets หรือข้อความวันที่/เวลา |
| CT `Qty Num` | แปลง AC เป็นตัวเลข โดยลบ comma ก่อน |
| CU `Time Slot` | ปัดลงเป็นช่วงชั่วโมงจาก CS เช่น 01:00–02:00 |
| CV `Sort Date` | วันที่จาก CS |
| CW `UOM Divisor` | lookup `UPPER(TRIM(Owner))|UPPER(TRIM(Item))` ใน `UOM_Master` |
| CX `UOM Qty` | CT ÷ CW เฉพาะเมื่อ CY เป็น `CALCULATED`; ถ้าไม่ผ่านจะว่าง |
| CY `UOM Status` | Allowed=true ให้ `CALCULATED`; ถ้าไม่พบคู่ Owner/Item ให้ `UNMAPPED_OWNER_ITEM`; กรณีพบแต่ไม่อนุญาตใช้สถานะจาก Master |
| CZ `UOM Rule` | กฎที่ lookup ได้จาก UOM_Master เช่น PICK_D, CASE_H, BLANK_D |
| DA `Shift` | Morning เมื่อเวลาอยู่ในช่วง 07:00–ก่อน 19:00; เวลาอื่นเป็น Night |
| DB `Shift Date` | ถ้าเวลาก่อน 07:00 ให้เลื่อนวันที่กลับหนึ่งวัน เพื่อให้เป็นกะกลางคืนของวันเริ่มกะ |
| DC `Sorter ID` | รหัสผู้ Sort ที่ดึงจาก BF |

`UOM_Master` ใช้ Key = Owner + `|` + Item และมีตัวหาร, Rule, Match Status และ Allowed การอ่านครั้งนี้พบ 9,485 mapping และทุกแถวที่มีข้อมูลเป็น `MATCHED`/Allowed=true; ตัวหารมีหลายค่า จึงห้ามรวม QTY ดิบแทน CX โดยไม่แปลง UOM ก่อน

### Wave, เวลา และ Location

- `Wave_Summary` สร้างรายชื่อ Wave จาก AP; Wave UOM รวม CX ทุกแถวของ Wave ส่วน Sorted UOM รวมเฉพาะแถวที่ CS มีเวลา
- Progress = Sorted UOM ÷ Wave UOM; Sort Lines นับแถวที่มี CS; Total Lines นับแถวทั้งหมดใน Wave
- ระยะเวลา Wave = เวลาสุดท้าย − เวลาแรกใน CS; Cycle/Line = ระยะเวลา ÷ (Sort Lines − 1); UOM/min = Sorted UOM ÷ ระยะเวลา
- Branch, Order, Location และ Item นับค่าไม่ซ้ำจาก BK, S, BM และ AF เฉพาะแถวที่มี CS
- สถานะ Wave คือ “ยังไม่เริ่ม” เมื่อ Sort Lines=0, “เสร็จแล้ว” เมื่อ Sort Lines=Total Lines, นอกนั้น “กำลัง Sort”
- `Time_Slot` รวมจำนวนบรรทัดและ CX ตาม CU โดยตัดแถวไม่มี CS; เพิ่มจำนวน Wave/Sorter ไม่ซ้ำและ UOM เฉลี่ยต่อบรรทัด
- `Location_Summary` รวม CX และนับบรรทัดตาม BM โดยตัดแถวไม่มี CS; `Dashboard_Data` เตรียม Top 10 Wave/Location และกราฟรายช่วงเวลาของ Morning/Night
- `Dashboard` มี 8 กราฟ ได้แก่ Top Wave, Wave ที่ใช้เวลานาน, UOM ตามเวลา/Location และกราฟเวลา/Top Location แยกกะ
- ป้าย Dashboard ปัจจุบันแสดง **Shift A = Morning** และ **Shift B = Night** รวมชื่อกราฟแยกกะและหัวตารางกราฟใน `Dashboard_Data`; ค่าต้นทาง `Sort_Data!DA` และ `Shift_Summary!A2:A3` ยังคงเป็น Morning/Night เพื่อให้สูตรกรองข้อมูลทำงาน ห้ามเปลี่ยนคอลัมน์ต้นทางเป็น A/B โดยไม่แก้เงื่อนไขสูตรให้ตรงกัน

### Productivity ของกะ Sort

- Morning = 07:00–19:00; Night = 19:00–07:00 ของวันถัดไป
- Active Hours ไม่ใช่เวลาที่มี event ทุกนาที สูตรนำ First Sort ถึง Last Sort มาตัดกับช่วงทำงานที่กำหนด: Morning 07:00–10:50, 12:00–16:00, 16:30–19:00; Night 19:00–22:50, 00:00–04:00, 04:30–07:00 วันถัดไป ดังนั้นเป็นเวลาที่ประเมินจากกรอบกะหลังหักช่วงพัก ไม่ใช่ผลรวมระยะห่างระหว่างแต่ละรายการ
- Sorted UOM รวม CX เฉพาะแถวที่มี CS และ DC ไม่ว่าง; Sorters นับ ID ไม่ซ้ำที่พบใน `Data_Employees!A2:A1000`; `Missing Sorter Lines` นับแถวมีเวลาแต่ DC ว่าง
- Team UOM/hr = Sorted UOM ÷ Active Hours; UOM/person/hr = Sorted UOM ÷ (Active Hours × Sorters)
- การ์ดเป้า 200 UOM/hr ตัดสินจาก Team UOM/hr ไม่ใช่ UOM/person/hr; ID ที่ไม่ว่างแต่ไม่มีใน Data_Employees ยังอาจเพิ่ม UOM ฝั่งตัวตั้ง แต่ไม่ถูกนับในจำนวน Sorters ฝั่งตัวหาร
- `Shift_Summary!B2` ใช้ MIN ของ Sort Date ใน CV และ Night ใช้วันเดียวกันจาก B2; ถ้า Sort_Data เก็บหลายวันพร้อมกัน แถวสรุปจึงอิงวันที่เก่าสุดในข้อมูลที่มีเวลา ไม่ได้เลือกวันที่ล่าสุดโดยอัตโนมัติ

ตัวเลขเป็นเพียงภาพ ณ วันที่อ่านชีต 15 ต.ค. 2569: Sort_Data มี 2,637 บรรทัดที่คำนวณ UOM ได้ในวัน Sort 14 ต.ค., รวม 4,926 UOM และ 62 Wave; V3 History มีสรุปถึง 14 ต.ค. พร้อม split SHIFT A/B ตัวเลขเหล่านี้เปลี่ยนได้เมื่อมีการนำเข้าข้อมูลใหม่ และไม่ใช่เงื่อนไขสูตร

### การตรวจแถวซ้ำ

หน้า Not Found จัดกลุ่มด้วย `User ID + วันที่` กลุ่มที่มีหลายแถวตรวจชั่วโมง H–AE ที่ซ้อนกัน, จำนวนแถว, ยอดซ้ำกันเป๊ะ และยอดชั่วโมงรวมเกิน 24 ความเสี่ยงสูงคือยอดกับชุดชั่วโมงซ้ำกันเป๊ะ, กลางคือมีชั่วโมงทับกัน, ต่ำคือไม่มีชั่วโมงทับกัน การ์ดนี้เป็นสัญญาณให้คนตรวจ ไม่แก้ยอดจริง และแสดงข้อมูลทุกวันที่มีวันที่กับ User ID โดยไม่สนตัวกรองหลัก

## การอ่าน/เขียนและบทบาท Apps Script

หน้าเว็บอ่านข้อมูลหลักแบบ CSV จาก Google Sheets โดยตรง; Apps Script `doGet()` ในโปรเจกต์ที่ผูกกับชีตเป็นเส้นทางเดิมและไม่ได้ถูกเรียกจากตัวโหลดปัจจุบัน (`RESULTS_API_URL` ว่างและ `fetchJsonpDashboard()` ส่งต่อให้ `V3Data`) ค่า Target ภายใน `doGet()` เป็นชุดเดิม เช่น Overall/Full Rack 170, Half Rack 200 และ Pick to Sort 170 จึงไม่ใช่ค่าปัจจุบันของหน้าเว็บซึ่งอ่าน `data/targets.json` เมื่อไม่มีแท็บ `V3 Target`

- Target โหลดจากแท็บ `V3 Target` ถ้ามีและอ่านครบ 21 keys; ถ้าอ่านไม่ได้ใช้ `data/targets.json`, แล้วจึงใช้ IndexedDB เป็นทางถอย
- Weight% ใช้ลำดับเดียวกันกับแท็บ `V3 Weight` จำนวน 18 keys; กลุ่ม Type/Zone ต้องรวม 100%
- การอ่าน metadata สดไม่พบแท็บ `V3 Target`, `V3 Weight` หรือ `Resigned` ใน Workbook นี้ ดังนั้น Target/Weight ปัจจุบันมาจาก JSON fallback จนกว่าแท็บจะถูกสร้างและอ่านได้
- `data/targets.json` ตั้งค่า endpoint สำหรับ write และ roster ไว้; ปุ่มบันทึก Target/Weight และฟอร์มทะเบียนจึงส่ง POST ไป Apps Script เมื่อใช้งาน
- `doPost()` ใน source ของโปรเจกต์ที่ผูกกับชีต (และสำเนา `apps-script-write.gs`) แยกคำขอ `targets`, `weights`, `rows`, `history`; ใช้ LockService, จำกัดค่า Target 1–1,000 และ Weight 0–100, ไม่เขียนทับช่องทะเบียนเดิมเว้นแต่ส่ง `overwrite`, และบันทึกการแก้ทะเบียนใน `V3 Write Log`
- History ใช้คีย์วันที่+โซน: เพิ่มข้อมูลใหม่, อัปเดตวันที่ล่าสุดใน batch, ข้ามวันที่เก่าที่มีอยู่แล้ว; หาก client รุ่นเก่าส่งเฉพาะยอดทั้งวัน จะเก็บ `_shiftBreakdown` เดิมไว้ไม่ให้ถูกเขียนทับ
- Apps Script source ที่ดูแลใน `apps-script-write.gs` และ Web App version 61 ใช้ `CACHE_VERSION` v52; Deployment ที่ Active ยังคงเปิดสิทธิ์ “ทุกคน” และรันในฐานะเจ้าของ

**ข้อควรตรวจเรื่องทะเบียน:** source version 61 ของ Deployment ที่ Active แสดงว่า `writeRosterV3_()` ต้องพบทั้งชีต `2ND` และ `Resigned` ก่อนเขียนทุกสถานะ แต่ metadata สดไม่มีชีต `Resigned` ใน Workbook หลัก ขณะที่ `source.js` อ่าน Resigned จากอีกสเปรดชีตหนึ่ง ดังนั้น POST ทะเบียนจะตอบ `missing sheet` แม้เป็นแถว active จนกว่าจะจัดปลายทางให้ตรงกัน

## จุดที่ต้องตัดสินให้ตรงกันก่อนเปลี่ยนกติกา

1. README บางส่วนยังอธิบายระบบก่อนมี Owner/Weight% และระบุ Target 24 keys; config ปัจจุบันมี Target 21 keys และ Weight 18 keys
2. Target/Weight tabs ไม่อยู่ใน metadata สด จึงใช้ค่าจาก `data/targets.json`; ถ้าสร้าง/เริ่มใช้แท็บทีม ให้ตรวจว่ามีครบทุก key ก่อนคาดหวังว่าค่านั้นจะทับ JSON
3. `Zone_V2!A:C` ระบุ AJ-AK เป็น Full Rack ของ Punthai แต่ `script.js`/`v1-engine.js` จัดโซน AJ-AK ไว้ใน Half Rack; ดังนั้น Pick Type ที่มาจาก `2ND!K` กับ Zone breakdown อาจจัดคนละ Type/Target ต้องตกลงว่าจะยึดข้อมูลทะเบียนหรือผังหน้าเว็บ
4. `Zone_V2!F:H` ยังมีแถว AA-AF แบบเก่า; V1 engine และ `metrics.js` ยังยอมรับรหัส AA-AE/HB ในบางเส้นทาง แต่ผังโซนหน้าเว็บปัจจุบันซ่อน AA-AE และถอด HB ออกจากกลุ่มโซน
5. หน้าไม่ถึงเป้าไม่นำ `M.isValidZoneRow()` มาคัด AF ก่อนรวม แต่หน้าหลักและ `metrics.aggregate()` มีเงื่อนไข Zone; AF>0 กับ Position ที่จับคู่ไม่ได้จึงอาจปรากฏเป็น Unknown ในหน้าไม่ถึงเป้า แต่ไม่เข้าค่าเฉลี่ยอีกเส้นทาง
6. สถานะเป้าบน Dashboard ถูกคำนวณจาก average ที่ปัดเป็นทศนิยม 1 ตำแหน่งแล้ว ส่วนหน้าแถวดิบบางหน้าตัดสินจากค่าไม่ปัด จึงต่างกันได้ใกล้ Target
7. V3 History เก็บสรุป BE ล่าสุดถึง 14 ต.ค. 2569 และมี split SHIFT A/B จาก Sort_Data; หาก source ดิบหรือแถว History ถูกลบ ข้อมูลระดับรายการจะกู้คืนไม่ได้
8. Apps Script version 61 ต้องมี `Resigned` ในไฟล์หลักก่อนเขียนทะเบียน แต่หน้าเว็บอ่านชีต Resigned จากอีกไฟล์ และ metadata ของไฟล์หลักไม่มีชีตนี้; POST ทะเบียนจึงมีแนวโน้มล้มเหลวทุกสถานะจนกว่าจะแก้ปลายทาง
9. Apps Script source ใน repository ใช้ `CACHE_VERSION` v52; `js/v1-engine.js` มี cache version ของเว็บคนละชั้นหนึ่ง การแก้ BE History ต้องตรวจทั้งการสร้าง split ที่หน้าเว็บและการเก็บ split ใน Apps Script
10. Apps Script Deployment ที่ Active คือ Script version 61; เปิดสิทธิ์ “ทุกคน” และรันในฐานะเจ้าของ โดย `data/targets.json` ใช้ URL deployment เดิม

## ข้อตกลงสำหรับการแก้ครั้งต่อไป

1. ระบุหน้าที่เปลี่ยนและสูตรที่ต้องใช้ก่อนแก้ แล้วตรวจว่าแถวนั้นใช้ V1 index, `V3Metrics.aggregate`, Weight% หรือ BE history
