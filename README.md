## Efficiency · เจาะลึกรายบุคคล · Incentive (ลอกจาก V2 คิดเลขด้วย V1)

สามหน้านี้ลอกองค์ประกอบจากหน้า `efficiency` / `individual` / `incentive` ของ V2
โค้ดแยกไฟล์ละหน้า (`v2-efficiency.js` · `v2-individual.js` · `v2-incentive.js` · `v2-duplicate.js`) ใช้ตัวช่วยร่วมผ่าน `window.V3Shared`
ซึ่งเปิดเพิ่มในรอบนี้ให้มี `zone` `zones` `zoneLabels` `visible` `statCards` `zoneTargetOf` เพื่อไม่ต้องคัดลอกกฎโซนของ V1 ไปเขียนซ้ำ

### Efficiency

การ์ด 4 ใบ (Efficiency เฉลี่ยรวม · สถานะภาพรวมพร้อม Gap · วันที่ผ่านเกณฑ์ Hit Rate · พนักงานที่ผ่านเกณฑ์)
→ กราฟเส้น % รายวันเทียบเส้นประ Baseline 100% → กราฟแท่งแยกกะและระบบ → **กราฟแยกประเภทการจ้าง คอลัมน์ AQ (V2 ไม่มี)**
→ ตารางรายวัน · ตารางอันดับรายโซน · ตารางประเภทการจ้าง

- % Efficiency = Productivity ÷ Target × 100 · ระดับวัน/กะ/ระบบใช้ `TARGETS.overall` ระดับโซนใช้ `zoneTargetOf()`
- เกณฑ์สี: ถึงเป้าเขียว · 90–99.9% ส้ม · ต่ำกว่า 90% แดง (ตัดสินจากค่าไม่ปัด ไม่ให้สีขัดกับตารางที่ขอบ 100%/90%)

### เจาะลึกรายบุคคล

โหมดเทียบทุกคน (การ์ด 5 ใบ + กราฟเทียบ Top 20 + ตาราง 15 คอลัมน์) → **กดที่ชื่อเพื่อเปิด Scorecard รายคนในหน้าเดียวกัน**

Scorecard มี: การ์ด 5 ใบ · กราฟเทรนรายวันของคนนั้น · **กราฟรูปแบบการทำงานรายชั่วโมงจากคอลัมน์ H–AE
(V2 ทำไม่ได้เพราะไม่มีข้อมูลรายคนรายชั่วโมง)** · ตารางโซนที่ทำพร้อมสัดส่วนและเทียบเป้าแต่ละโซน
· ตารางรายวันที่มีคอลัมน์ **"เหตุผลที่ไม่เข้าเฉลี่ย"** · ข้อมูลทะเบียนจาก 2ND (ชื่อเล่น สังกัด หน้าที่ อายุงาน Ready/Training)
· Remark แดงถ้าอยู่ในชีต Resigned · เปอร์เซ็นไทล์เทียบกลุ่ม

เกณฑ์ตัดสินใช้สองระดับให้สอดคล้องกันทั้งหน้า — **ระดับรายคน** เทียบ Target ของโซนหลัก (เหมือนเมนูไม่ถึงเป้า)
· **ระดับรายวัน/รายแถว** เทียบ Target ของโซนที่ทำในแถวนั้น

### Incentive

แผงตั้งเกณฑ์แก้ได้บนหน้าเว็บ (โหมดจ่าย · อัตราแต่ละ Tier · ชั่วโมงและวันขั้นต่ำ) เก็บใน `localStorage`
คีย์ `pickProductivityIncentiveConfig:v3` มีปุ่มคืนค่าเริ่มต้น → การ์ด Tier 4 ระดับ (Bronze 100–114% · Silver 115–129% · Gold 130–149% · Platinum ≥ 150%)
→ การ์ดสรุป 5 ใบ → โดนัทสัดส่วน Tier · กราฟงบตามสังกัด → ตารางรายคน

- **เป็นการประมาณการบนหน้าเว็บเท่านั้น ไม่ผูกกับระบบจ่ายเงินจริง และไม่เขียนกลับ Google Sheet** (เขียนกำกับไว้ในหน้า)
- มีเกณฑ์ขั้นต่ำกันคนชั่วโมงน้อยที่ค่าเฉลี่ยเหวี่ยงสูง และแยกให้ชัดว่าใครถูกตัดเพราะเกณฑ์ขั้นต่ำ ไม่ใช่เพราะไม่ถึงเป้า

## เทรน สัปดาห์ / เดือน

ลอกองค์ประกอบมาจากหน้า `trend` ของ V2 (`app.js` renderTrendPage 6151-6241) เมนูอยู่กลุ่ม 1 ต่อจาก สรุปผล & Present

- โหมด **รายวัน** กราฟกางทีละเดือนพร้อมปุ่มเลื่อนเดือน (ทั้งชุดมี 240 วัน ใส่ใบเดียวอ่านไม่ออก)
  ตารางยังเห็นทุกวัน · วันที่มีแถวเข้าเฉลี่ยน้อยกว่า 5 แถวขึ้น ⚠️ เพราะค่าเฉลี่ยเหวี่ยงง่าย
  (ของจริงที่เจอ: 22/01/2569 ขึ้น 204.0 หยิบ/ชม. จาก 3 แถว ถ้าไม่เตือนจะอ่านเป็นวันที่ทำได้ดีที่สุด)
  · คอลัมน์ที่ไม่มีความหมายในโหมดวันถูกเปลี่ยน — "เฉลี่ย/วัน" เป็น "เฉลี่ย/คน" และ "คนมากสุด/วัน" เป็น "คนที่มีผลงาน"
- การ์ดสรุป 5 ใบ — Productivity งวดล่าสุด · เปลี่ยนแปลง WoW/MoM · ยอดหยิบงวดล่าสุด · งวดที่ดีที่สุด · งวดที่ถึงเป้า
- กราฟผสม แท่ง = ยอดหยิบ (คอลัมน์ E) เส้นแดง = Productivity เส้นประ = Target สองแกนแบบ V2
- กราฟที่สองเป็นแท่ง % เปลี่ยนแปลงเทียบงวดก่อน เขียวขึ้น แดงลง
- ตารางเทียบงวด 10 คอลัมน์ เรียงใหม่ → เก่า กดหัวคอลัมน์เรียงใหม่ได้
- **กางทุกงวดที่มีข้อมูลเสมอ ไม่หุบตามตัวกรองวันที่** (เหมือน V2) แท่งสีเข้มคืองวดที่ครอบช่วงวันที่ที่เลือก
  และงวดนั้นมีป้าย "ช่วงที่เลือก" ในตาราง · ตัวกรองระบบ (BPS/PTT) และกะ ยังมีผลตามปกติ
- สัปดาห์เริ่มวันจันทร์เหมือน V2 ป้ายเป็น `14/9–20/9` · เดือนเป็นปี พ.ศ. เช่น `ก.ย. 2569`

**จุดที่ตัวเลขต่างจาก V2 โดยตั้งใจ** — V2 คิด Productivity ของงวดเป็น *เฉลี่ยของค่าเฉลี่ยรายวัน*
(`app.js:6136` เฉลี่ยของ `avg_prod` ซึ่งเองก็เฉลี่ยมาอีกชั้น) V3 ใช้สูตร V1 คือ **ผลรวม AF ของแถวที่ AF > 0 ÷ จำนวนแถวนั้น
รวม sum/count ครั้งเดียว** ยิ่งจำนวนแถวของแต่ละวันในงวดต่างกันมาก สองวิธียิ่งให้ผลต่างกันมาก
มีข้อความบอกไว้ในโน้ตใต้กราฟด้วย

## ไม่ถึงเป้า (แยกตามโซน)

เมนูอยู่ใน **กลุ่ม 3** เป็นปุ่มแรก ใช้คลาส `.nav-danger` ที่ทำให้เห็นเด่นกว่าเมนูอื่นตลอดเวลา
(พื้นชมพู ขอบแดง แถบแดงด้านซ้าย ตัวหนา) และมี **ป้ายตัวเลขจำนวนคนที่ยังไม่ถึงเป้า** อัปเดตตามตัวกรองด้านบน
โดยไม่ต้องเปิดหน้านั้นก่อน (`updateBelowTargetBadge()` ใน `insights.js` เรียกทุกครั้งที่เรนเดอร์)


ลอกองค์ประกอบมาจากหน้า `belowtarget` ของ V2 (`app.js` renderBelowTargetPage 5936-6033 และ drawBelowTargetChart 6035-6104)
เมนูอยู่กลุ่ม 2 ใช้ `data-page="below-target"` คลาส `nav-alert` เหมือน V2 · โค้ดอยู่ใน `insights.js` ฟังก์ชัน `belowTargetPage()`

องค์ประกอบตามลำดับเหมือน V2

1. การ์ดสรุป 5 ใบ (`.zone-summary` / `.zone-stat`) — ไม่ถึงเป้ากี่คน · สัดส่วน % · ช่องว่างเฉลี่ย · โซนที่ต้องดูก่อน · โซนที่มีคนไม่ถึงเป้า n/m
2. กราฟแท่งซ้อนต่อโซน แดง = ไม่ถึงเป้า (คน) เขียว = ถึงเป้า (คน) เรียงโซนที่แย่สุดขึ้นก่อน สูงสุด 20 โซน
3. โน้ตเกณฑ์การนับ
4. ตารางโซน — ไม่ถึงเป้ากี่คน / คนทั้งหมด / สัดส่วน / ค่าเฉลี่ยโซน / Target โซน / ช่องว่างเฉลี่ย / Total Pick
5. ตารางรายคนที่ไม่ถึงเป้า เรียงคนที่ห่างจากเป้ามากที่สุดขึ้นก่อน

กฎการนับ (เป็นของ V1 ทั้งหมด)

- ค่าเฉลี่ยรายคน = ผลรวมคอลัมน์ AF เฉพาะค่า > 0 ÷ จำนวนแถวนั้น (`v1-engine.js` finalizePickerRows_ 1752) ไม่เฉลี่ยค่าเฉลี่ยซ้ำ
- **ไม่ถึงเป้า = ค่าเฉลี่ย < Target ของโซน** เท่ากับเป้านับว่าผ่าน (`v1-engine.js` finalizeBucket_ 2111)
- คนที่ไม่มีแถวเข้าเฉลี่ย (AF > 0) ไม่ถูกตัดสิน ตามที่ V1 ทิ้งคนที่ `count = 0`
- Target ของโซนมาจาก `getZoneTarget(zoneKey, groupKey)` คือดูค่าที่ตั้งรายโซนก่อน ถ้าไม่ได้ตั้งจึงใช้ Target ตามประเภทงาน
  แก้ได้ที่ปุ่ม **⚙️ ตั้งค่า Target** (มีช่องครบทั้ง 17 โซน)
- คนหนึ่งคนนับครั้งเดียว ยึด **โซนหลัก** = โซนที่มีแถวเข้าเฉลี่ยมากที่สุด เหมือนที่ V2 เทียบรายคนกับโซนหลัก
  จำนวนคนรายโซนจึงบวกกันได้เท่ากับยอดรวมพอดี ไม่นับซ้ำ
- แถวที่คอลัมน์ AH ไม่ตรงกฎโซนของ V1 ไปอยู่กอง **Not Found** ซึ่งใช้ Target รวม ไม่ใช่โซนจริง
  จึงไม่ถูกเลือกเป็น "โซนที่ต้องดูก่อน" และมีข้อความเตือนไว้ในโน้ต

## Target ของทีม (ทุกคนเห็นเลขชุดเดียวกัน)

แหล่งความจริงของ Target คือไฟล์ [`data/targets.json`](data/targets.json) ที่ push ขึ้นไปพร้อมเว็บ
**แก้ไฟล์นี้แล้ว push = ทุกคนเห็นค่าใหม่พร้อมกัน** ไม่ต้องให้ใครไปกดตั้งค่าเอง

เดิม Target เก็บอยู่ใน `localStorage` / cookie / IndexedDB ของเครื่องแต่ละคน ใครปรับก็เห็นคนละเลข
แล้วมาถามกันว่าทำไมของตัวเองไม่เหมือนของคนอื่น (เว็บเป็น static + อ่าน Sheet แบบ read-only
จึงไม่มีที่เก็บค่ากลางบนเซิร์ฟเวอร์ และตามข้อตกลง 17/09/2569 ไม่ใช้ Apps Script/PropertiesService แบบ V2)

- ทุกเครื่องโหลด `data/targets.json` ตอนเปิดหน้า แล้ว **ทับค่าที่เก็บไว้ในเครื่องเสมอ**
  (`loadTeamTargets()` ใน `script.js`) ค่าของทีมจึงชนะทุกครั้งที่รีเฟรช
- ถ้าโหลดไฟล์ไม่ได้ (ไม่มีไฟล์ / เปิดแบบ `file://`) **หน้าไม่ล่ม** จะถอยไปใช้ค่าที่เคยเก็บใน IndexedDB
  ตามพฤติกรรมเดิม แล้วขึ้นชิปแดงบอกว่ากำลังใช้ค่าในเครื่อง ไม่เงียบไว้ให้เข้าใจผิดว่าตรงกับทีม
- `?v=` ของ `data/targets.json` ไม่ต้องบั๊ม เพราะโหลดด้วย `?t=<เวลา>` + `cache:'no-store'` อยู่แล้ว

ชิปบนแถบตัวกรอง (`#teamTargetChip`) บอกตรง ๆ ว่าเลขที่เห็นมาจากไหน — ถ้าเงียบไว้
สองคนเห็นเลขต่างกันแล้วไม่มีทางรู้ว่าเพราะอะไร

| ชิป | หมายความว่า |
|---|---|
| ✅ เขียว `Target ของทีม · <วันที่>` | ตรงกับของทีม ทุกคนเห็นเลขเดียวกัน · วันที่คือ `updatedAt` ของไฟล์ แสดงเป็น d/m/พ.ศ. |
| 🔶 ส้ม `Target ส่วนตัว · คนอื่นไม่เห็นเลขชุดนี้` | เครื่องนี้ปรับเองหลังรับค่าทีม มีปุ่ม **ใช้ค่าของทีม** กดกลับได้ทันที |
| ⚠️ แดง `โหลด Target ของทีมไม่ได้` | อ่านไฟล์ไม่สำเร็จ กำลังใช้ค่าในเครื่องนี้ |

ช่อง **🎯 เป้า Target** และปุ่ม **⚙️ ตั้งค่า Target** ยังใช้ได้เหมือนเดิม แต่ถือเป็น
**การปรับดูเฉพาะเครื่องนี้** และจะถูกค่าของทีมทับเมื่อรีเฟรช

ในหน้าต่างตั้งค่า กล่อง `#targetTeamInfo` **บอกแค่ "อัปเดตล่าสุด &lt;วันที่&gt;"** ของค่าชุดที่กำลังใช้
(21/09/2569) ไม่มีปุ่มคัดลอก ไม่มีปุ่มคืนค่า และไม่มีขั้นตอนให้ผู้ใช้ทำต่อ —
เพราะคนใช้งานไม่ควรต้องรู้ว่าเบื้องหลังเก็บค่าไว้ที่ไหน
(รอบก่อนมีปุ่ม 📤 คัดลอกค่าเป็นไฟล์ targets.json กับปุ่มคืนค่าเดิมของเครื่อง ถอดออกแล้วเพราะผู้ใช้บอกว่ายากเกินไป
คีย์ `pickProductivityTargetsLocalBackup:v3` ที่ใช้คู่กันถูกลบทิ้งให้เองตอนโหลดหน้า ไม่ค้างเป็นขยะ)

### วิธีเปลี่ยน Target ให้ทั้งทีม — กดบันทึกในหน้าเว็บ

ปรับเป้าในหน้าเว็บ → กด **💾 บันทึกเป็นค่าของทีม** (มีทั้งในหน้าต่าง ⚙️ ตั้งค่า Target
และบนชิปตอนที่ค่ายังไม่ตรงกับทีม) → คนอื่นรีเฟรชก็เห็นตาม

ปุ่มนี้ยิงไปที่ [`apps-script-target-write.gs`](apps-script-target-write.gs) ซึ่งเขียนลงแท็บ
**`V3 Target`** ในสเปรดชีตเดียวกับ Results Master แล้วหน้าเว็บอ่านแท็บนั้นกลับมาแบบอ่านอย่างเดียว

ลำดับการอ่านค่า Target (ใน `loadTeamTargets()`)

1. **แท็บ `V3 Target`** ในสเปรดชีต — ค่าสด อ่านผ่าน gviz โดยระบุ **ชื่อแท็บ** จึงไม่ต้องรู้ `gid`
   (เหตุที่ `source.js` เลี่ยง gviz — ตัดแถวตาม filter และทำรหัสผสมตัวอักษรหาย — ไม่กระทบที่นี่
   เพราะแท็บนี้มีแค่ชื่อคีย์กับจำนวนเต็ม 24 แถว ไม่มี filter ไม่มีรหัสพนักงาน)
   · ยอมรับเฉพาะตอนอ่านได้ **ครบทั้ง 24 คีย์** เพราะ Target ครึ่ง ๆ กลาง ๆ อ่านผิดยิ่งกว่าไม่ใช้เลย
2. **`data/targets.json`** — ค่าสำรอง และเป็นที่เก็บ config ปลายทางเขียน (`write.url` / `write.token` / `sheetTab` / `sheetId`)
3. **IndexedDB** ตามพฤติกรรมเดิม (กันหน้าไม่มี Target ใช้)

จะยิงไปอ่านแท็บก็ต่อเมื่อตั้ง `write.url` ไว้แล้ว — ถ้ายังไม่ตั้ง แท็บนั้นยังไม่มี
การยิงไปก็ได้ error เปล่า ๆ ทุกครั้งที่เปิดหน้า · และ **ถ้าสคริปต์พังหรือถูกลบ
หน้าเว็บยังอ่าน Target ได้ตามปกติ** แค่บันทึกใหม่ไม่ได้

#### ติดตั้งครั้งเดียว

1. เปิด Google Sheet ของ Results Master → **ส่วนขยาย (Extensions) → Apps Script**
   (สร้างเป็นโปรเจกต์แยกจาก `apps-script-roster-write.gs` เพื่อลบของเดิมได้อิสระ)
2. วาง [`apps-script-target-write.gs`](apps-script-target-write.gs) ทั้งไฟล์ แล้วแก้ `WRITE_TOKEN` เป็นข้อความสุ่มของตัวเอง
3. **Deploy → New deployment → Web app** · Execute as: **Me** · Who has access: **Anyone**
4. เอา URL (`.../exec`) กับโทเคน ใส่ใน `data/targets.json` ช่อง `write.url` / `write.token` แล้ว push

แท็บ `V3 Target` กับแท็บ log `V3 Target Log` สคริปต์สร้างให้เองตอนบันทึกครั้งแรก ไม่ต้องสร้างมือ

#### ขอบเขตและความเสี่ยงที่รู้ตัว

- สคริปต์เขียนได้**เฉพาะแท็บ `V3 Target` และ `V3 Target Log`** ไม่แตะ Results Master / 2ND / Update name / Zone_V2
- รับเฉพาะ **24 คีย์ที่กำหนดไว้** และค่าต้องเป็นจำนวนเต็ม **1–1000**
  · คีย์แปลกปลอมหรือค่านอกช่วง **ปฏิเสธทั้งคำขอ ไม่เขียนบางส่วน**
- ทุกช่องที่ค่าเปลี่ยนถูก log ไว้พร้อมเวลาและผู้บันทึก
- **URL กับโทเคนถูก commit ลง repo** เพื่อให้ทุกคนกดบันทึกได้โดยไม่ต้องตั้งค่าเอง
  ใครเปิดเว็บหรือเปิด repo ได้จึงเปลี่ยน Target ได้ด้วย
  ตัวกันความเสียหายคือขอบเขตที่แคบ + log + version history ของ Sheet ซึ่งย้อนได้
  ถ้าไม่ยอมรับความเสี่ยงนี้ ให้ย้าย `write` ไปเก็บใน `localStorage` ของแต่ละเครื่องแทน
  (แลกกับที่คนอื่นจะกดบันทึกไม่ได้)
- POST ส่งเป็น `text/plain` เพื่อให้เป็น simple request ไม่มี preflight
  เพราะ Apps Script ตอบ 302 ไป `googleusercontent` ซึ่ง preflight ผ่านไม่ได้ — **อย่าเปลี่ยนเป็น `application/json`**

## เรียงข้อมูลในตาราง

ทุกตารางที่ใช้ `V3Shared.table()` กดหัวคอลัมน์เพื่อเรียงได้

- กดครั้งแรก **มาก → น้อย** ครั้งที่สองน้อย → มาก ครั้งที่สามกลับลำดับตั้งต้นของหน้านั้น
  (ต้องมีสถานะที่สาม เพราะบางตารางจัดลำดับมาก่อนแล้ว เช่นการ์ด Not Found ดันคนที่ออกแล้วไปท้าย)
- ค่าว่างไปท้ายรายการเสมอ คอลัมน์ที่แปลง `null` เป็น 0 เพื่อแสดงผล ให้ใส่ `sortValue` กำกับไว้
- เรียงข้อความไทยด้วย `localeCompare(…, 'th')` · กดด้วย Enter/Space ได้ และตั้ง `aria-sort` ให้ screen reader
- Export CSV ออกตามลำดับที่เห็นบนจอ

## พนักงานใหม่ / พนักงานเก่า

เกณฑ์อายุงานใช้กฎเดียวกับ V1 (`buildTenuredPickerBenchmark` ใน `script.js`)

- `anchor` = วันล่าสุดที่มีข้อมูล · `cutoff` = anchor ลบ **90 วัน** (ไม่ใช่ 3 เดือนปฏิทิน)
- **พนักงานใหม่** = วันเริ่มงานหลัง cutoff · **พนักงานเก่า** = วันเริ่มงานก่อนหรือเท่ากับ cutoff
- วันเริ่มงานยึด `Update name` คอลัมน์ H เหมือน V1 ก่อน แล้วใช้ `2ND` คอลัมน์ G เป็นตัวสำรอง
  (V1 ไม่ได้อ่านคอลัมน์นี้ ส่วนนี้เพิ่มเข้ามาเพื่อให้ครอบคลุมคนมากขึ้น) ถ้าไม่มีทั้งสองที่จึงใช้วันแรกที่พบผลงาน
  ใน Results Master เหมือน `firstSeen` ของ V1 ทำให้ทุกคนที่มีผลงานถูกจัดกลุ่มได้ ไม่มีใครตกกลุ่ม

แต่ละหน้ามี KPI 5 การ์ด, กราฟ Chart.js, การ์ดสรุป "สิ่งที่ควรทำต่อ" และตารางรายคนที่ค้นหา/Export CSV ได้

- **พนักงานใหม่**: เส้นการพัฒนา (Learning Curve) ตามสัปดาห์ที่นับจากวันแรกที่มีผลงาน เทียบ Target
  และค่าเฉลี่ยของพนักงานเก่า · กราฟ Productivity รายคน · คอลัมน์ "สัปดาห์แรก → ล่าสุด" บอกว่าดีขึ้นเท่าไร
- **พนักงานเก่า**: แนวโน้มรายเดือนของกลุ่ม (แท่ง Total Pick + เส้น Productivity + เส้น Target) ·
  กราฟ 10 อันดับสูงสุดและ 10 อันดับต่ำสุด · คอลัมน์ "เทียบเดือนก่อน" บอกว่าเดือนล่าสุดดีขึ้นหรือแย่ลง

ทุกกลุ่มยังใช้สูตร V1: Total Pick = ผลรวมคอลัมน์ E · Productivity = ผลรวมคอลัมน์ AF ของแถวที่ AF > 0
หารด้วยจำนวนแถวนั้น รวม sum/count ครั้งเดียวทั้งรายคน รายสัปดาห์ และรายเดือน

## รหัสที่ต้องตามข้อมูล (Not Found)

ทั้งหน้าพนักงานใหม่และพนักงานเก่ามีการ์ด **⚠️ รหัสที่ต้องตามข้อมูล** ดึงคนที่ยังมีช่องว่างหรือ Not Found ออกมาแยก
พร้อมบอกว่าต้องไปเติมที่ชีตไหน คอลัมน์ไหน

| สิ่งที่ขาด | ต้องไปเติมที่ |
|---|---|
| ไม่มีใน 2ND | เพิ่มแถวในชีต `2ND` (B รหัส, C ชื่อ) |
| ไม่มีชื่อ | `2ND` คอลัมน์ C ชื่อ-นามสกุล |
| ไม่มีวันเริ่มงาน | `Update name` คอลัมน์ H (หรือ `2ND` คอลัมน์ G) |
| กะ Not Found | `Results Master` คอลัมน์ AG |
| สังกัดว่าง | `Results Master` คอลัมน์ AI |
| BU ว่าง | `Results Master` คอลัมน์ AJ |
| Type Pick ว่าง | `Results Master` คอลัมน์ AK |
| Zone ว่าง | `Results Master` คอลัมน์ AH (Position) |

- การ์ดบอกจำนวนคนและ **Total Pick ที่กระทบ** เพื่อจัดลำดับว่าควรตามใครก่อน
- แถบ pill ด้านบนสรุปว่าขาดอะไรกี่คน ชี้เมาส์ค้างเพื่อดูว่าต้องไปเติมที่ไหน
- ใช้ปุ่ม **ซ่อนคนที่ออกแล้ว** ร่วมกับการ์ดนี้ได้ เพราะคนที่ลาออกแล้วไม่จำเป็นต้องตามข้อมูล
- กด **Export CSV** เพื่อเอารายการไปไล่แก้ใน Sheet ได้เลย
- ผลงานของคนเหล่านี้ **ไม่ถูกตัดออกจากยอดใด ๆ** ตามกฎ V1 แต่ KPI ที่ต้องใช้ข้อมูลนั้นจะเชื่อถือไม่ได้

V3 อ่านข้อมูลอย่างเดียว จึงกรอกข้อมูลกลับเข้า Sheet จากหน้าเว็บไม่ได้ ใช้ Export CSV แทน

## หน้าต่างกรอกข้อมูล (เก็บไว้ในเครื่อง ยังไม่ส่งเข้า Sheet)

ในการ์ด "รหัสที่ต้องตามข้อมูล" (หน้าพนักงานใหม่/พนักงานเก่า) และการ์ด "รหัสพนักงานที่ยังไม่มีทะเบียน"
(หน้า Not Found & ตรวจข้อมูล) มีปุ่ม **✏️ เติมข้อมูล** ต่อแถว เปิดฟอร์มกรอกในหน้าเดียวกันได้เลย

ตามที่ผู้ใช้สั่งไว้ **ฟอร์มนี้ยังไม่ยิงข้อมูลออกไปที่ Google Sheet** ไม่มีการเรียก Apps Script
และไม่มีกล่องตั้งค่า URL/โทเคนในหน้าเว็บ ที่กรอกจะเก็บใน `localStorage` ของเครื่องนั้น
แล้วกด **Export CSV ที่กรอกไว้** เอาไปวางในชีตเอง

| เลือก | ช่องที่ให้กรอก | ปลายทางที่ต้องไปวาง |
|---|---|---|
| ยังทำงานอยู่ | 10 ช่อง (ชื่อ, ชื่อเล่น, สังกัด, หน้าที่, วันเริ่มงาน, Status Work, Zone, Pick Type, BU, กะ) | ชีต **2ND** คอลัมน์ C–M |
| ⛔ ลาออกแล้ว | 3 ช่อง (ชื่อ, วันที่พ้นสภาพ, หมายเหตุ) | ชีต **Resigned** คอลัมน์ A รหัส · B ชื่อ · H วันพ้นสภาพ |

- กด ⛔ ลาออกแล้ว แล้วบันทึก → แถวนั้นขึ้น Remark **สีส้ม "⛔ ออกแล้ว · กรอกในเว็บ"** ทันที
  แยกจากสีแดงที่หมายถึง "ยืนยันแล้วจากชีต Resigned" และถูกซ่อนตามปุ่ม **ซ่อนคนที่ออกแล้ว** เหมือนกัน
- คนที่กรอกในเว็บว่าออกแล้วจะ **ค้างอยู่ในการ์ดต่อ** จนกว่าจะเอาไปใส่ในชีต Resigned จริง
  (นับแยกไว้ที่ป้าย "กรอกในเว็บรอใส่ใน Sheet") เพื่อไม่ให้ลืมว่างานยังไม่จบ
- วันที่พิมพ์ได้ทั้ง `31/08/2026`, `31/08/2569` (พ.ศ.) และ `2026-08-31` · อ่านไม่ออกจะเตือนไม่ให้บันทึกมั่ว
  · เว้นว่างได้ถ้าไม่รู้วัน จะขึ้นว่า "ไม่ทราบวันที่"
- CSV ส่งออก **วันที่พ้นสภาพเป็น ปี ค.ศ. แบบ `yyyy-mm-dd`** เพื่อให้วางลงชีตแล้วไม่เพี้ยนตามรูปแบบวันที่
  และมีคอลัมน์ "ปลายทางที่ต้องไปกรอก" บอกชีต/คอลัมน์ของทุกแถว
- สลับปุ่มไปมาไม่ทำให้ที่กรอกไว้หาย ค่าของอีกสถานะยังถูกเก็บไว้และติดไปใน CSV ด้วย
- คนที่อยู่ในชีต Resigned อยู่แล้ว ฟอร์มจะตั้งค่าเป็น "ลาออกแล้ว" ให้และขอแค่ชื่อ
  ถ้าคนนั้นกลับมาทำงาน ต้องแก้ที่ชีต Resigned ก่อน เพราะชีตเป็นแหล่งจริง หน้าเว็บทับไม่ได้ (มีข้อความบอกไว้ในฟอร์ม)

### AF ขึ้นกับ AK — ระวังตอนกรอก Pick Type

ตรวจสูตรจริงใน Results Master แล้วพบว่า AG–AK เป็น `XLOOKUP` ที่ดึงจาก 2ND

| Results Master | สูตร |
|---|---|
| AG กะ | `XLOOKUP(D, '2ND'!B:B, '2ND'!M:M, "Not Found Data")` |
| AH Zone | `XLOOKUP(D, '2ND'!B:B, '2ND'!J:J, "Not Found Data")` |

| AK Pick Type | `XLOOKUP(D, '2ND'!B:B, '2ND'!K:K, "Not Found Data")` |
| AF AVERAGE | `IF(AK="ช่วยงานส่วนอื่น","Not Count", IF(AND(G>3,F<1000),F,"Not Count"))` |

เขียนค่าทับ AG–AK จะทำให้สูตรหายถาวร จึงต้องเติมที่ 2ND แล้วให้สูตรอัปเดตเอง

- มีปุ่ม **ซ่อนคนที่ออกแล้ว** บนแถบเกณฑ์ของทั้งสองหน้า ใช้ร่วมกัน กดครั้งเดียวมีผลทั้งคู่

  จึงแปลงแยกด้วย `dateValueMonthFirst()` ใน `source.js`
- ถ้าอ่านไฟล์นี้ไม่ได้ (สิทธิ์แชร์ต่างกัน) จะไม่ทำให้ทั้งหน้าล่ม แท็บนี้ตั้ง `optional: true` ไว้
  เว็บจะทำงานต่อโดยไม่มี Remark และรายงานไว้ใน `source.warnings`
  ซึ่งตอนนี้ **แสดงบนหน้าจอแล้ว** (แถบสถานะแหล่งข้อมูล และในการ์ดรหัสที่ต้องตามข้อมูล)
  เพราะถ้าเงียบไว้ ทุกคนจะดูเหมือนยังทำงานอยู่ทั้งหมด
- รหัสในชีตนี้ 14 แถวไม่มีวันพ้นสภาพ จะขึ้นว่า **⛔ ออกแล้ว ไม่ทราบวันที่** ไม่ใช่ขีดกลางลอย ๆ
- คนที่ออกแล้วและรู้ชื่ออยู่แล้ว **ไม่ถูกนับเป็นงานค้าง** ในการ์ดรหัสที่ต้องตามข้อมูล
  (เดิมนับทั้ง 8 ช่อง ทำให้รายการยาวเกินจริง) เหลือเฉพาะคนที่ยังไม่รู้ว่าเป็นใคร
- การจับคู่รหัสระหว่างชีตใช้ `trim()` ตรงตัวทั้งสามที่ (Results Master D, 2ND B, Resigned A)
  ตรวจข้อมูลชุดปัจจุบันแล้ว **ไม่มีรหัสที่พลาดเพราะตัวพิมพ์เล็ก-ใหญ่หรือศูนย์นำหน้า**

- `apps-script-roster-write.gs`: Apps Script สำหรับเติมข้อมูลกลับชีต 2ND (ผู้ใช้ Deploy เอง ไม่ถูกเรียกจากเว็บโดยตรง)
- `apps-script-target-write.gs`: Apps Script ปลายทางเขียน **Target ของทีม** — เว็บเรียกตัวนี้เมื่อกดปุ่มบันทึก เขียนได้แค่แท็บ `V3 Target` กับแท็บ log
- `v2-roster-write.js`: ฟอร์มเติมข้อมูลในหน้าเว็บ + กล่องตั้งค่าปลายทาง เก็บค่าใน localStorage
- `parked/sections.html`: มาร์กอัปของหน้าที่ถอดออกชั่วคราว เก็บไว้เพื่อนำกลับทีละหน้า เว็บไม่โหลดไฟล์นี้

ข้อมูลและสูตร (ยึดของ V1 ทั้งหมด)

- `v1-engine.js`: ตัวคำนวณ V1 ภายใน read-only adapter ทำงานใน Worker
- `script.js`: การแสดงผลและการรวมข้อมูล V1
- `source.js`: อ่าน CSV export ครบทุกแถว (ไม่ใช้ gviz ที่อาจตัดแถวตาม filter และทำรหัสผสมตัวเลข/ตัวอักษรหาย)
- `data-worker.js` / `data-client.js`: โหลด snapshot, แคชแยก V3, อ่านสดและคำนวณเบื้องหลัง
- `metrics.js` / `insights.js`: การเจาะลึกจากรายการต้นทาง
- `data/snapshot.json`: ข้อมูลจริง ณ เวลาที่ระบุในไฟล์ รวมชื่อ/รหัสพนักงาน ใช้สำหรับเปิดทดลองและสำรอง
- `data/targets.json`: **ค่าสำรองของ Target + config ปลายทางเขียน** (`write.url` / `write.token` / `sheetTab` / `sheetId`) · ค่าที่ใช้จริงอ่านจากแท็บ `V3 Target` ในชีต

ไม่มีการแก้ไฟล์ใน `Pick Productivity` (V1) และ `Pick Productivity_V2` จากงานนี้ — ไฟล์ของ V2 ถูกอ่านเท่านั้น

## สถานะ V1 / V2 และ Apps Script เดิม (ข้อตกลง 17/09/2569)

**ยังไม่ลบอะไรทั้งนั้น** แผนคือทำ V3 ให้สมบูรณ์ก่อน แล้วจึงเลิกใช้และลบ V1 ทีหลัง

สิ่งที่ตรวจไว้แล้ว เพื่อให้ตอนลบไม่ต้องไล่ใหม่

- **V3 อ่านข้อมูลผ่าน CSV export ตรง ๆ ไม่ผ่าน Apps Script**
  (บรรทัด `preconnect` ไป `script.google.com` ที่ค้างมาจาก V1 ถูกลบออกจาก `index.html` แล้ว)
  · ข้อยกเว้นเดียวที่เพิ่มเข้ามา 21/09/2569 คือ **ปุ่มบันทึก Target ของทีม** ที่ยิงไป
  `apps-script-target-write.gs` ซึ่งเป็นโปรเจกต์ Apps Script **แยกจากของ V1/V2** จึงลบของเดิมได้อิสระเหมือนเดิม
  · การ *อ่าน* ข้อมูลทุกอย่างรวมถึง Target ยังไม่ผ่าน Apps Script เลย
- **V1 และ V2 ยังเรียกอยู่** — V1 `script.js` เรียก `AKfycbyby7nOGMZe-w8p…`
  ส่วน V2 `app.js` เรียกตัวเดียวกันบวก `AKfycbyM0IVjD6Eo867r…` ลบแล้วสองหน้านั้นพังทันที
- **สคริปต์เดิมไม่เขียนลงชีต** ตรวจ `apps-script-api.gs` (V1/V2) และ `bigquery_to_json.gs` (V2)
  ไม่พบ `setValue` / `setValues` / `appendRow` / `clearContent` / `deleteRow` เลย เป็น API อ่านอย่างเดียว (`doGet`)
  → **ข้อมูลใน Results Master ไม่ได้มาจากสคริปต์** ลบแล้วข้อมูลในชีตไม่หาย
- ของที่จะหายเมื่อลบ: trigger `syncPickMastersDaily` และ `warmDashboardCache`
  (sync ลง CacheService/PropertiesService ไม่ใช่ลงชีต) และ **shared targets / excluded zones ของ V2**
  ที่เก็บใน `PropertiesService` ซึ่งกู้ไม่ได้
- ยังไม่ได้ยืนยัน: โปรเจกต์ที่ deploy อยู่จริงอาจมีโค้ด/trigger ไม่ตรงกับไฟล์ในเครื่อง
  ก่อนลบให้เปิด Apps Script ของชีตดู **Triggers** และ **Manage deployments** อีกครั้ง
- แนะนำลำดับตอนจะลบ: ลบ trigger → Archive deployment (URL ตายแต่โค้ดอยู่) → รอสองสามสัปดาห์ → ลบจริง
- `apps-script-roster-write.gs` ของ V3 ควร Deploy เป็น **โปรเจกต์แยก** ไม่วางทับของเดิม
  เพื่อให้ลบของเดิมได้อิสระ

## Deploy ภายหลัง

ยังไม่ได้สร้าง Git repository หรือ push V3 ตามที่ผู้ใช้จะสร้างปลายทางใหม่หลังทดลองผ่าน สามารถใช้ static hosting เช่น GitHub Pages; วางไฟล์ให้ครบรวม data/snapshot.json ไม่มีขั้นตอน Deploy Apps Script และไม่ต้อง Run SQL ให้ Google Sheets แชร์แบบที่ผู้ชมมีสิทธิ์อ่าน export ได้ หากอ่านสดไม่ได้เว็บจะแสดง snapshot พร้อมสถานะอัปเดตไม่สำเร็จ

V1 และ V2 เดิม รวมทั้งข้อมูล BigQuery ไม่ได้ถูกแก้ไขหรือลบจากงานนี้
